What Beacon Is Missing

Beacons are generated via Menhir. That reframes the question — not "what does the standalone package's own roadmap say," but "what does Menhir need before it can actually generate one."

Revision note — the first pass of this page analyzed the wrong layer; see below.

The real gap is smaller than it looks. Menhir already shipped a concrete semantic-object system for engineering documents (WorkArtifact, 2026-08-03) with identity, lifecycle, relationships, and full MCP tool support. orientation — the exact concept a generated Beacon would need — is already sitting on that system's own deferred-type list. Nothing abstract needs designing from zero; something concrete needs promoting.

Three points in time, one unresolved until now

None of these three documents reference each other. Read in isolation, each looks complete. Read together, two of them contradict.

  1. 2026-06-29–30
    archolith-beacon v0 shipsShippedStandalone PyPI package. Static beacon.yaml, five read-only MCP tools, ManifestBeaconProvider. Zero commits since.
  2. 2026-07-11
    "LSP for Agents" proposalNever resolvedArgues Beacon should be a decoupled protocol, Menhir only an optional backend. "Do not make Beacon a menhir feature." Status: needs a product decision from ctharvey. No decision was ever recorded against it directly.
  3. 2026-07-25
    Semantic Object & Beacon architecture decisionsAccepted baselineDecision queue #56. Redefines Beacon as Menhir-native: "the authorized adaptation and delivery boundary" that generates Orientation — an Adaptive Semantic Object minimizing Time-to-Competence. Confirms zero Beacon code exists in src/menhir at the time. All operational detail explicitly deferred.

Neither the July 11 nor the July 25 direction has a single line of implementing code. The difference is that July 25 is the later, explicitly "accepted" decision, and it's the one you just confirmed.

What already exists: the Artifact Semantic Model

Shipped 2026-08-03 — four days before this conversation, and with no cross-reference to either Beacon document above. It is, in every load-bearing respect, a working instance of what the July 25 decision describes in the abstract.

  • :WorkArtifact — stable artifact_uuid identity independent of path, a real lifecycle (PROPOSED → REVIEWED → APPROVED → IMPLEMENTING → IMPLEMENTED, plus SUPERSEDED/DEFERRED from any state), typed relationships (ABOUT, DECLARES), and addressable owned OpenQuestion records.
  • Already MCP-exposed: list_artifacts, get_artifact, get_artifact_relationships, list_artifact_questions, supersede_artifact, transition_artifact, link_artifacts. A future Beacon provider would not need a single new Menhir API — these already cover onboarding, guardrails, and concept-explanation queries.
  • work_artifact.py's own docstring: "Deliberately not generalized further yet. Deferred: adr, migration, rfc, orientation." Orientation is already named, in the exact system Beacon would need to read from.Same discipline that added `handoff` on 2026-08-03: "a type earns its place by having instances," not by being imaginable.
  • The design doc's own open question 1 — whether ABOUT allows more than one subject per artifact — was left unresolved because "CurrentPlanView is unbuilt, so the grouping pressure that would decide this has not been felt yet." A Beacon/Orientation generator is exactly the consumer that would apply that pressure.

The path, in order

Each step only makes sense after the one before it. Skipping ahead means guessing at a shape nothing has tested.

  1. Run the corpus check handoff ran

    handoff became a real type because 14 undifferentiated handoff documents already existed across two repos. Before orientation earns the same promotion, the equivalent question needs an answer: does orientation-shaped content already exist informally? Every project's .agent/README.md "Quick Start" section is a plausible candidate corpus — but that's a hypothesis to check, not an assumption to build on.

    Why first: the artifact system's whole discipline is "earns its place by having instances." Skipping this check is exactly the mistake the system was designed to prevent.

  2. Promote orientation to a real artifact_type

    If the corpus check finds real instances, derive orientation's shape contract from them — the same way handoff's contract was derived from what its 14 real documents actually had in common (a title, nothing else universal), not from what seemed reasonable to require.

    Why here: this reuses 100% of existing graph schema, lifecycle, and MCP surface. No new Menhir subsystem, just one more entry in ARTIFACT_TYPES plus a shape contract in artifact_shape.py.

  3. Build MenhirBeaconProvider in the standalone package

    The BeaconProvider Protocol already exists in archolith-beacon's provider/base.py with exactly the five methods needed. A Menhir-backed implementation calls list_artifacts(type=orientation) / get_artifact instead of parsing static YAML — the MCP tool layer (beacon_project_overview, etc.) doesn't change at all.

    Why last: this is the only step that touches the beacon repo, and it has nothing real to consume until step 2 exists.

Don't build yet

  • More hand-written beacon.yaml manifests. This was my first recommendation on this page, and it's close to the exact anti-pattern the July 11 review called out — a static file that "rots," authored instead of generated.
  • The full abstract Semantic Object framework (disclosure profiles, revision/event formats, generic Adaptive composition beyond Orientation). The July 25 decision doc itself defers all of this. Building it ahead of a concrete consumer repeats the exact mistake CurrentPlanView is avoiding by staying unbuilt.
  • A resolution to the July 11 proposal as written. It's superseded by the July 25 acceptance, but nobody has gone back and marked it SUPERSEDED in the artifact graph — worth a five-minute fix so a future reader doesn't hit the same contradiction cold.
